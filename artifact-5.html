Thinking in Systems

Working through real-world ML data challenges — the issues that actually break models in production

Objective

Rather than defining concepts, this artifact shows me reasoning through three progressively harder data challenges an ML engineer faces in the real world — and refining my approach based on feedback at each step. It's built as an AI-guided coaching session across three escalating scenarios, and it's written for a technical audience: recruiters, hiring managers, and fellow AI/ML practitioners who care less about textbook definitions and more about how someone thinks when a model misbehaves.

The Three Scenarios

Each scenario escalates in difficulty, and in each one the naive move turns out to be the trap:

  1. 01
    Missing Data — Customer Churn

    With 15% of tenure values missing, I chose imputation over dropping rows to avoid losing 1,500 records. I planned to confirm the distribution before choosing median versus mean, added a "was-missing" flag to preserve the signal that a value was absent, and compared strategies using cross-validation rather than training accuracy.

    → Insight: inspect the data before assuming a fix

  2. 02
    Extreme Class Imbalance — Fraud Detection

    With only 0.5% fraud, I flagged the "99.5% accuracy" trap immediately and switched to precision, recall, and PR-AUC. I weighed SMOTE against class weights, used stratified splitting to preserve the rare class, and tuned the decision threshold to what the fraud team could realistically absorb operationally.

    → Insight: match the metric to the problem, not the default

  3. 03
    Concept Drift — Credit Risk

    When a deployed model degraded, I separated two layered problems — economic drift versus an unseen gig-worker representation gap. I proposed recency-weighted retraining plus feature rework, and added continuous drift monitoring (PSI / KL divergence) with an automated retraining trigger.

    → Insight: design for change; a deploy is never "finished"

Value Proposition

This artifact shows I can move past textbook definitions into production reality: diagnosing why a model fails, matching the technique to the actual problem instead of reaching for the fanciest option, and designing systems that expect change rather than assuming a one-time deploy. It's the applied counterpart to the conceptual ML-versus-DL analysis — where that piece asks "which tool fits?", this one asks "what do you do when the tool you shipped starts to break?"

Reflection
The naive move is almost always the trap — casually dropping missing data, trusting accuracy, or treating a deployed model as finished.

The through-line I discovered across all three scenarios is that the real work is inspecting before assuming, matching the tool to the problem, and building for the fact that conditions will shift. Each scenario rewarded restraint over reflex: the fastest answer — drop the rows, trust the accuracy score, ship and move on — was consistently the one that would have quietly broken the system later.
